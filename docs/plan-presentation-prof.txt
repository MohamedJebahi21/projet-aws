1. INTRODUCTION & CADRAGE DU SUJET (2 MINUTES)
--------------------------------------------------------------------------------
Ce qu'il faut dire à l'oral :
"Bonjour Monsieur. Nous vous présentons aujourd'hui notre projet de déploiement
d'infrastructure cloud sur Amazon Web Services.

L'objet évalué aujourd'hui est l'INFRASTRUCTURE, et non la complexité métier
de l'application. Notre charge de travail est une application de gestion de
bibliothèque universitaire que nous avons conçue pour être multi-composants,
stateless et déployée sur une architecture web 3-tiers résiliente.

Toutes les contraintes imposées par le module ont été respectées :
- 100% de l'infrastructure est décrite en code avec Terraform (IaC modulaire).
- Déploiement multi-AZ en région us-east-1.
- Contraintes du Learner Lab respectées (rôle LabRole, gestion des sessions,
  et budget de 50$ strictement préservé grâce à notre stratégie de destruction).
- Après destruction totale, une seule commande reconstruit toute la plateforme."

Documents à ouvrir sur l'écran :
-> docs/fiche-livrable-1.md


--------------------------------------------------------------------------------
2. PRÉSENTATION DE L'ARCHITECTURE TECHNIQUE 3-TIERS (3 MINUTES)
--------------------------------------------------------------------------------
Ce qu'il faut montrer :
Ouvrir docs/architecture.md et commenter le schéma :

Point 1 : TIER 1 - ENTRÉE & RÉSEAU PUBLIC
- VPC dédié 10.0.0.0/16 avec Internet Gateway.
- 2 sous-réseaux publics (us-east-1a et us-east-1b).
- Point d'entrée unique : Application Load Balancer (ALB).
- Seul l'ALB est exposé sur Internet (port 80).

Point 2 : TIER 2 - APPLICATIF EN SOUS-RÉSEAUX PRIVÉS
- 2 sous-réseaux privés hébergeant un Auto Scaling Group (EC2 t3.micro).
- Capacité : minimum 2 instances réparties sur 2 zones de disponibilité.
- Launch Template avec profil imposé LabInstanceProfile et User Data automatisé.
- Application Javalin stateless (Java 17) écoutant sur le port 8080.

Point 3 : TIER 3 - PERSISTANCE RELATIONNELLE ISOLÉE
- 2 sous-réseaux privés base de données isolés (sans accès Internet).
- Instance managée Amazon RDS PostgreSQL 15 (db.t3.micro) chiffrée gp3.
- Sauvegardes automatisées quotidiennes.
- Multi-AZ désactivé pour économiser 50% du coût RDS (justifié dans l'ADR-03).

Point 4 : STOCKAGE S3 & ACCÈS SORTANT ÉCONOMIQUE
- Bucket S3 privé chiffré (SSE-S3 AES-256) pour les artefacts et reçus PDF.
- VPC Gateway Endpoint S3 : gratuit et direct (le trafic S3 ne passe pas par Internet).
- Micro-instance NAT EC2 (t3.micro) avec iptables au lieu du NAT Gateway managé
  qui aurait coûté 32$/mois (ADR-01).

Point 5 : MATRICE DE SÉCURITÉ STRICTE
- Chaînage des Security Groups par référence (alb-sg -> app-sg -> rds-sg).
- ZÉRO port d'administration (22, 3389, 5432) ouvert sur 0.0.0.0/0.
- Secret RDS généré par Terraform et stocké dans S3 chiffré, jamais dans Git.

3. DÉMONSTRATION EN DIRECT N°1 : APPLICATION & RÉPARTITION MULTI-AZ (3 MINUTES)
--------------------------------------------------------------------------------
Actions à réaliser en direct devant le prof :
1. Ouvrir le navigateur sur l'URL de l'ALB :
   http://<ALB_DNS_NAME>

2. Montrer le bandeau supérieur de l'interface :
   "Regardez ici : le badge vert indique en direct l'Availability Zone et l'Instance ID
    qui répondent à ma requête."

3. Actualiser la page plusieurs fois (F5) :
   Montrer que la zone alterne entre us-east-1a et us-east-1b.
   "L'ALB équilibre bien la charge entre nos deux zones de disponibilité."

4. Faire une action métier :
   - Aller sur l'onglet 'Livres' -> Rechercher ou ajouter un livre.
   - Aller sur 'Nouveau Prêt' -> Valider un emprunt.
   - Montrer la confirmation : "Un reçu PDF a été généré en mode headless sans GUI
     et archivé automatiquement dans notre bucket Amazon S3 privé."

4. DÉMONSTRATION EN DIRECT N°2 : ÉPREUVE DE RÉSILIENCE (3 MINUTES)
--------------------------------------------------------------------------------
C'est le moment fort pour impressionner le professeur !

Actions à réaliser :
1. Dans un premier terminal, lancer le flux continu de requêtes :
   python scripts/load_test.py --url http://<ALB_DNS_NAME> --users 20 --duration 60

2. Dans un second terminal, injecter la panne en direct :
   python scripts/chaos_inject.py terminate

Ce qu'il faut expliquer pendant l'exécution :
- "Monsieur, nous venons de détruire brutalement une des deux instances EC2 en direct."
- "Regardez le terminal du test de charge : AUCUNE ERREUR 5xx. Le taux de succès reste à 100%."
- "L'ALB a détecté la coupure en 18 secondes et a basculé tout le trafic sur l'instance survivante."
- "Et dans la console EC2 / Auto Scaling Group, une nouvelle instance de remplacement
   a été immédiatement commandée par l'ASG pour rétablir la capacité requise de 2."

Mesure prouvée : Remplacement complet en 2 min 45 s (< 5 min contractuel).

5. DÉMONSTRATION EN DIRECT N°3 : SUPERVISION CLOUDWATCH & ALARMES (2 MINUTES)
--------------------------------------------------------------------------------
Actions à réaliser :
1. Ouvrir la console AWS -> CloudWatch -> Dashboards -> 'biblio-dev-supervision-dashboard'.
2. Montrer les 4 graphiques clés :
   - Cibles saines vs non saines (HealthyHostCount).
   - Utilisation CPU de l'Auto Scaling Group.
   - Nombre de requêtes HTTP et erreurs 5XX de l'ALB.
   - Nombre de connexions actives à la base RDS PostgreSQL.

3. Montrer les Alarmes CloudWatch :
   - Alarme 1 : biblio-dev-alarm-unhealthy-hosts (déclenchée si cible défaillante).
   - Alarme 2 : biblio-dev-alarm-high-cpu (déclenchée si charge CPU > 70%).

4. Démonstration de détection d'incident (Semaine 13) :
   - "Si un incident survient, nous n'avons pas besoin de lire le code : le tableau
      de bord nous indique immédiatement la couche défaillante."

================================================================================
AIDE-MÉMOIRE : RÉPONSES AUX QUESTIONS PIÈGES DU PROFESSEUR
================================================================================

QUESTION 1 : "Pourquoi avez-vous mis une instance NAT plutôt qu'un NAT Gateway AWS ?"
RÉPONSE :
"Le NAT Gateway managé AWS coûte 0,045 $/heure (~32 $/mois). En un seul mois, il aurait
consommé 65% de notre crédit total de 50$. Nous avons déployé une micro-instance t3.micro
avec iptables (~0,010 $/h) couplée au S3 Gateway Endpoint gratuit. C'est documenté dans
notre ADR-01."

QUESTION 2 : "Comment transmettez-vous le mot de passe de la base sans le commiter ?"
RÉPONSE :
"Terraform génère un mot de passe aléatoire (random_password) et l'écrit directement dans
un objet S3 chiffré SSE-S3. Au démarrage de la VM, le script User Data utilise le rôle
LabInstanceProfile pour lire ce fichier et l'injecter dans un fichier d'environnement
protégé en chmod 600. Il n'apparaît ni dans Git, ni dans le User Data, ni dans la console."

QUESTION 3 : "Pourquoi avoir désactivé le Multi-AZ sur RDS ?"
RÉPONSE :
"Le Multi-AZ sur RDS double immédiatement le tarif horaire de la base de données. Pour
respecter notre budget contractuel de moins de 35$ sur le semestre, nous avons choisi
PostgreSQL en Single-AZ avec des sauvegardes automatiques quotidiennes et des snapshots
manuels, offrant un RPO de 24h et un RTO de moins de 11 minutes (ADR-03)."

QUESTION 4 : "Si la route /health renvoie 503, que fait l'ALB ?"
RÉPONSE :
"L'ALB effectue un contrôle toutes les 15 secondes. Au bout de 2 échecs consécutifs
(unhealthy_threshold = 2), il marque la cible 'Unhealthy' et cesse immédiatement de lui
envoyer du trafic. L'Auto Scaling Group, dont le health check est basé sur l'ELB, déclenche
alors le recyclage et le remplacement automatique de l'instance."

QUESTION 5 : "Avez-vous cliqué dans la console AWS ?"
RÉPONSE :
"Non, monsieur. 100% des ressources portent le tag 'ManagedBy = Terraform'. La console AWS
ne nous sert que de moniteur de vérification visuelle. Tout est déployé par scripts/deploy.ps1
et détruit par scripts/destroy.ps1."
